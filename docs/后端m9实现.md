# 后端 M9 实现说明：网页搜索工具调用（路线 A）

> 日期：2026-10-14 | 上游：[M9开发计划.md](M9开发计划.md)（决策 A–G）、[二期prd.md](二期prd.md) §8
> 范围：tool_calls 表 + sessions.tool_enabled（user_version 5）/ tools 模块（360 抓取 + trafilatura 提取 + 流式判别）/ engine 两轮编排 / SSE tool_call 事件 / observability tool_call 字段

## 1. 实现要点

### 1.1 搜索源选型（spike 实录，`server/spikes/m9_web_search_spike.py`）

- **DDG 本机网络不可达**（无代理，超时）→ 改 Bing：实测按 TLS/IP 反爬投毒——httpx、curl_cffi（chrome 指纹）、连续请求后的系统 curl 均拿到**标题正确但结果无关**的页面（apple.com 出现 0 次）
- 百度首请求成功随后 1.4KB 验证页（cookie 预热无效）；搜狗 5KB 反爬墙；searxng 公共实例不可达
- **360（so.com）可用但高频撞「访问异常页面」**（密集测试约 50%，重试 2 次挽回一部分）；结果块 `res-list` 切片解析，真实 URL 取 `data-mdurl` 属性（href 是跳转链）
- **HTTP 走 subprocess 系统 curl**（SecureTransport 指纹通过率最高），trafilatura 只负责解析 HTML 字符串（其 fetch_url 同样会被指纹拦截）

### 1.2 模型侧验证（spike part 3）

- 决策轮 tool_call 形态与 2026-10-09 基线一致（空 think 壳 + `<tool_call>` 文本块，llama-cpp 0.3.36 不走 `message.tool_calls` 字段）
- Qwen3 模板把 tool 角色渲染为 **user 段 + `<tool_response>` 包裹**；历史 assistant 的 think 壳由模板自动剥离
- `prompt_render` 不传 tools 时口径偏差 140 token（工具定义段漏算）——`render_prompt`/`segment_tokens` 已加 `tools` 参数对齐，工具定义计入 system 段

### 1.3 调用循环（chat/engine.py）

- `_chat_with_tools`：决策轮（tools + system 尾追加日期提示段 + 当前 user 追加 `/no_think`）→ `ToolCallDetector` 流式前缀判别 → 命中则 SSE `tool_call` 事件 → `web_search` → 回答轮（assistant tool_call 原文 + tool 角色结果，摘 tools）
- 判别器三态 pending/text/tool：缓冲至可判别，偏离前缀立即回吐（普通回答流式体验不损）；坑点——`</think>` 闭标签逐字符到达，壳体途中形态需用截断前缀正则（`\s*(?:<(?:/(?:t…)?)?)?\s*`）匹配，否则单字符流误判
- 坑点（实机抓获）：llama-cpp 模板把 `<think>` **预开进 prompt**，决策轮流可能以 `</think>` 开头（模型只补闭标签）——判别器首版只认 `<think>`/`<tool_call>` 两种开头，`</` 开头被判「偏离前缀」整段泄漏；已改为三候选（`<think>`/`</think>`/`<tool_call>`）截断前缀等待 + 首标签即闭标签时跳过壳体
- 坑点：360 PC 端会 **IP 级封禁**（302 到 qcaptcha，真浏览器同撞），移动端 m.so.com 风控独立不受影响——搜索改双端点按序兜底，解析器兼容两套结构（PC `li.res-list`+`data-mdurl` / 移动端 `div.g-card.res-list`+`data-pcurl`，推荐卡等无真实 URL 块滤除）
- 无工具调用时决策轮即最终轮（观测数据 `_copy_result` 搬回共享 result）；usage/计时/prompt_messages 恒取最终轮
- 降级：搜索失败 → `search_error`，「搜索失败：原因」喂回模型向用户说明（实测：模型诚实回答不知道）；JSON 非法 → `parse_error`，原文回吐当普通文本；均落库不阻断
- assistant 消息只落最终回答文本（决策 K）；SSE 只加 `tool_call` 单事件，回答轮首个 token 即中间态结束

### 1.4 存储与接口

- user_version 4→5：tool_calls 表（results 快照 JSON，仿 retrievals）+ sessions.tool_enabled（`_M9_SESSION_COLUMNS` 幂等 ALTER）；删会话级联
- `PATCH /sessions/{id}` 加 `tool_enabled?`（三字段全空 400 EMPTY_UPDATE）；列表项/会话响应加字段；observability 加 `tool_call` 两态字段
- config 常量：`tool_search_top_n=5` / `tool_fetch_pages=2` / `tool_page_max_chars=1500` / `tool_inject_max_tokens=768` / 超时 10s / 重试 2 次间隔 2s
- 依赖：新增 trafilatura（requirements.txt）；httpx 未采用（指纹投毒）

## 2. 验证记录

- 判别器单元冒烟：tool_call 各粒度切片（1/2/3/7/100 字符）零泄漏识别、带壳普通文本完整回吐、真实思考放弃判别、壳空白变体、stop 中断残余回吐 ✓
- 主链路冒烟（临时库，显式 DB_PATH）：迁移 v4→v5 → 开开关问诺贝尔奖 → SSE 序列 meta→tool_call{query}→token→done 正确 → tool_calls 落库（search_error 降级路径实测：撞墙 3 次 5.1s，错误喂回模型）→ observability.tool_call 正确 → prompt_messages 角色序列 system/user/assistant/tool ✓
- **成功路径已端到端验证（2026-10-15，fkjs-14b）**：问「今天天气怎么样」→ tool_call{query} → 360 移动端兜底取回 5 条结果 + Top-2 正文提取 → success 落库 → 模型基于结果作答；中间态/TracePane 工具区块正常。附注：360 按出口 IP 地理定位，首条 AI 天气卡直接给了北京本地结果（且卡内容为缓存旧日期，数据时效性见 §3）
- 决策概率性：冒烟第三次模型未调用工具直接回答（基线决策正确率 87.5%，属预期方差）；fkjs-14b 身份注入未干扰工具决策（决策 F 回归通过）

## 3. 遗留与边界

- 360 PC 端会 IP 级封禁（302 qcaptcha，真浏览器同撞），已由 m.so.com 移动端双端点兜底化解（2026-10-15）；如需更稳定可配置化换 Tavily 类 keyed API（计划决策 B 记录选型史）
- 360 AI 问答卡（ai.so.com）内容为大模型缓存，日期可能与实际不符而模型照单转述——如需可在注入时过滤聚合卡或附当前日期让模型核对（未做，按需评估）
- 正文提取已在真实成功搜索上端到端验证（Top-2 抓取正常，第三条空走 snippet 兜底）
- /no_think 失效（模型真实思考）时判别器放弃判别，tool_call 标记会泄漏到气泡（罕见，已知边缘）
- tool response 追加在已截断 prompt 之后，极端情形超 n_ctx 由 `tool_inject_max_tokens` 兜底，不做二次滑窗
- 搜索是同步 subprocess 不响应 stop_event（秒级）；回答轮可正常被 stop；两轮各自 acquire 生成锁
