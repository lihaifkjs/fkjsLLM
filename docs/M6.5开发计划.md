# M6.5 开发计划：上下文摘要压缩

> 状态：已完成（批次 0–3 全部落地，real 联调通过） | 日期：2026-10-10
> 上游文档：[二期prd.md](二期prd.md)（§5 M6.5、§3 调用链标签页预留）、[技术方案.md](技术方案.md)（§1.1 分层约束 / §5.2 全局生成锁 / §5.3 上下文管理）、[后端m3实现.md](后端m3实现.md)（滑窗截断现状）、[后端m5实现.md](后端m5实现.md)（观测数据口径）、[前端m5实现.md](前端m5实现.md)（观测数据通道）
> 范围：上下文超阈值时用本机 14B 将旧对话增量压缩为摘要，最终上下文 = system prompt + 摘要 + 最近 N 轮原文；滑窗/摘要两策略全局可切换；压缩调用全程可观测，被压缩历史有 UI 有损标识。

## 1. 目标

- 新增「摘要压缩」上下文策略，与现有滑窗硬截断并存、全局可切换（教学对比）
- 摘要增量生成：已压缩部分不重复压缩，每轮只把新溢出的消息追加进既有摘要
- 压缩本身是一次 LLM 调用：压缩前/后 prompt 与 token 数、耗时落库，调试抽屉「调用链」标签页填实展示
- 消息列表对被摘要覆盖的历史消息给出有损标识（褪色 + 角标）
- 触发阈值与最近 N 轮的 N 值经 spike 实测调优后定为常量，写入技术方案

## 2. 现状盘点（2026-10-10 调研结论）

**后端**：
- 滑窗是 `server/chat/context.py` 的 29 行纯函数 `fit_window`，唯一调用点在 `chat/engine.py::_build_prompt`——压缩路径的天然分流点；被截断消息不删库，仅拼 prompt 时跳过
- 观测落库汇合点在 `chat/engine.py::_wrap`（finally 回填 messages 观测列）；压缩调用的观测可复用 `GenerateResult` 同口径字段
- 全局生成锁 `_gen_lock`（`model_manager/manager.py`）不可重入：**压缩必须作为主生成前的独立调用**，两次 acquire 之间存在并发插入窗口（决策 D）
- 加列迁移有既定模式（`_M5_COLUMNS` 清单 + `PRAGMA user_version`，当前 v2）；新建表只需加入 `_SCHEMA` + 版本号 +1
- 参数全局单份存 settings 表（`params/presets.py`），`SamplingParams`（`config.py`）加枚举字段即可放行 `GET/PUT /api/params`
- token 计数用 `model_manager.count_tokens`（模型实例 tokenize，滑窗同口径）

**前端**：
- 调试抽屉「调用链」标签页当前是纯占位 `PlaceholderPane.vue`（`DebugDrawer.vue` TABS 配置化），替换为新 pane 组件即可，不动容器（一期 §3.7 硬约束）
- `useObservability` 数据通道成熟，观测类型加可空字段后各 pane 的 null 降级模式照抄
- 消息气泡操作区在 `MessageBubble.vue`，M5「调试」按钮同款位置可加压缩标识；`ChatMessage` 为契约类型
- 参数面板 `ParamsView.vue` 手写 `.field` 块，加 `el-select` 枚举项 + `onSave` 补丁即可；mock 的 `saveParams` 白名单自动放行新字段
- mock 观测构造 `buildObservability`（`api/mock.ts`）扩展压缩字段即可自洽；策略行为可按参数分支模拟

## 3. 数据存储（SQLite，app.db 迁移 user_version 2→3）

新建 compressions 表，同时承担「压缩历史记录」与「当前生效摘要缓存」双职责（会话当前摘要 = 该 session 最新一条记录）：

```sql
CREATE TABLE compressions (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  session_id INTEGER NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
  trigger_message_id INTEGER,          -- 触发本次压缩的 assistant 消息 id（关联调用链展示）
  prev_summary TEXT NOT NULL DEFAULT '',  -- 压缩输入：既有摘要（增量追加，首次为空）
  source_messages TEXT NOT NULL,       -- 压缩输入：本次新纳入的消息渲染文本（JSON [{role, content}]）
  source_prompt TEXT NOT NULL,         -- 压缩调用的完整渲染 prompt（展示压缩前 prompt）
  summary TEXT NOT NULL,               -- 产出：新摘要（即当前生效摘要）
  covered_upto INTEGER NOT NULL,       -- 摘要覆盖到的最大 message id（增量游标）
  source_tokens INTEGER,               -- 压缩前 token 数（被压缩部分）
  summary_tokens INTEGER,              -- 压缩后 token 数（摘要本身）
  input_tokens INTEGER, output_tokens INTEGER,   -- 压缩调用观测（M5 口径精简版）
  ttft_ms REAL, prefill_ms REAL, decode_ms REAL,
  created_at REAL NOT NULL
);

CREATE INDEX idx_compressions_session ON compressions(session_id, id);
```

sessions 表不加列；滑窗策略下摘要数据保留但不用，切回即恢复。

## 4. 压缩策略设计（chat 层，`context.py` 扩展）

**触发与分流**（`chat/engine.py::_build_prompt` 内）：
1. 策略为 sliding_window → 现状 `fit_window` 不变
2. 策略为 summary → 计数 system + 全部历史，未超 budget（= `n_ctx − max_tokens`）则不动作
3. 超限 → 保留最近 N 轮原文，溢出部分中 `id > covered_upto` 的消息为「新增待压缩」：
   - 有新增（或尚无摘要）→ 发起一次压缩 generate（串行、非流式消费完），落库 compressions
   - 无新增（边界）→ 直接复用既有摘要
4. 最终上下文 = system prompt + 摘要（独立 system 段，prompt_messages 中可辨识）+ 最近 N 轮原文
5. **双兜底**：压缩后仍超 budget（N 轮原文过大/摘要过长）→ 对最近 N 轮再走 `fit_window`；压缩调用异常 → 整体降级滑窗，对话不中断

**压缩 prompt 模板**（初稿，spike 调优）：

```
system: 你是对话压缩器。将【既有摘要】与【新增对话】合并为一份连贯摘要，
        保留关键事实、用户偏好、结论与待办，丢弃寒暄与细节复述。
user:   【既有摘要】{prev_summary}
        【新增对话】{source_messages 渲染}
        【要求】仅输出合并后的摘要，不超过 {max_summary_chars} 字。
```

压缩参数固定：低 temperature（初值 0.2）、max_tokens 初值 512、不带会话 system prompt——随 compressions 落库可溯。

**常量**（`server/config.py`，spike 后定值）：`SUMMARY_KEEP_ROUNDS`（N，初值候选 4）、`SUMMARY_MAX_TOKENS`（512）、`SUMMARY_TEMPERATURE`（0.2）。触发阈值复用 budget = `n_ctx − max_tokens`，不另设。

**等待体验**：压缩发生在主生成前、SSE meta 帧之前，期间前端仅显示「思考中」；不新增 SSE 事件类型（M9 才引入工具调用事件），压缩耗时体现在 TTFT 拉长并在调用链展示。压缩与主生成两次独立 acquire `_gen_lock`，接受其间插入窗口（决策 D）。

## 5. 批次 0：spike 实测调优（2026-10-10 已完成）

| 步骤 | 内容 |
| --- | --- |
| 0.1 | `server/spikes/summary_compression_spike.py`：10 轮构造对话（埋 8 个可核查事实），跑全量 ×2（t0.2/t0.7）+ 增量两步压缩；结果存 `summary_compression_result.json` |
| 0.2 | `server/spikes/summary_no_think_spike.py`：验证关闭 think 块的方式 |

**实测结论**：
- 摘要质量合格：全量 t0.2/t0.7 与增量两步均保留关键事实（姓名/技术栈/deadline/n_ctx/SQLite 等），增量第二步有轻微细节丢失（n_ctx 数值未保留）——有损性的实证教学样本
- 耗时：单次压缩 35–67s（14B CPU，输出 340–480 token），其中 think 块占一半以上
- **think 处理**：`create_chat_completion` 不支持 `chat_template_kwargs`（TypeError）；user 内容尾加 ` /no_think` 有效（33 token / 7.2s vs 对照 128 token / 13.3s），产出空 `<think></think>` 壳由 `strip_think` 剥离
- **定值**：`SUMMARY_KEEP_ROUNDS=4`、`SUMMARY_MAX_TOKENS=512`（/no_think 后摘要实测 ≤300 token，余量充足）、`SUMMARY_TEMPERATURE=0.2`（t0.2 与 t0.7 质量相当，取确定性）

## 9. 决策记录（2026-10-10 已确认）

- **A. 配置粒度**：全局开关——`SamplingParams` 加 `context_strategy`（sliding_window / summary），走 settings 表，所有会话共用
- **B. 摘要生成**：增量追加——compressions 表 `covered_upto` 游标记录覆盖范围，每轮只压缩新溢出消息，与既有摘要合并
- **C. 存储**：新建 compressions 表（user_version→3），兼任压缩历史与当前摘要缓存；sessions/messages 表不动；滑窗策略下摘要保留可回切
- **D. 并发窗口**：压缩与主生成两次独立 acquire `_gen_lock`，接受其间被并发请求插入的窗口（局域网单用户场景，插入方拿到 409 提示即可）
- **E. 摘要注入形式**：作为独立 system 段拼在 system prompt 之后、N 轮原文之前，prompt_messages 中可辨识（调用链/Prompt 预览天然可见）
- **F. 常量而非参数**：N 值、摘要 token 预算、压缩 temperature 为 config 常量（spike 定值），不暴露给用户面板——面板只有策略开关
- **G. 无新增 SSE 事件**：压缩期间前端无中间态，耗时计入 TTFT 并在调用链展示

## 10. 风险与坑点

- **压缩质量**：14B CPU 上单次压缩预计秒级到十几秒，用户等待无中间态——摘要 max_tokens 必须硬约束，防长摘要拖慢且再次撑爆 budget
- **增量游标一致性**：`covered_upto` 必须取「本次实际纳入压缩的最大 message id」，删消息/会话后游标不可回退；会话删除靠 ON DELETE CASCADE 清 compressions
- **双兜底路径**：压缩后仍超限与压缩异常两条降级路径都要走 `fit_window`，漏一条超长会话直接 500
- **锁窗口**：压缩结束到主生成 acquire 之间被插入时，主生成基于的摘要仍是正确的（摘要不依赖并发方），无需补偿——但要在文档中明示该窗口存在
- **token 计数口径**：`fit_window` 数裸 content、M5 观测数渲染后文本（含模板开销），压缩触发的「超限」判断沿用裸 content 口径（与滑窗一致），展示层用渲染口径，两者并存需在实现文档注明
- **契约变更**：消息列表响应包一层 `{messages, summary_covered_upto}` 是破坏性变更，mock 与 real 必须同步改，M3–M6 前端所有消费点逐一核对
- **400 detail 包装**：`context_strategy` 非法值走 `presets` 校验 400，前端 `parseErrorBody` 已兼容同形状
