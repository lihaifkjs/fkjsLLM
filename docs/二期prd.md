## 3. M5：可观测性面板落地

将一期预留的调试抽屉 5 个标签页从占位填实：

1. **Prompt 预览**：完整模型输入按角色（system / user / assistant）着色渲染
2. **Token 统计**：新增各段（system / 历史 / 当前消息）token 占比；每轮输入/输出 token 数一期已实现，本标签页做聚合展示
3. **性能指标**：新增首 token 延迟（TTFT）、prefill / decode 分段耗时；token/s 一期已实现，本标签页做聚合展示
4. **生效参数快照**：该条消息实际使用的推理参数（含全局默认值来源标注）
5. **调用链**：M5 阶段保持占位，M7 填入检索调用记录，M6.5 填入压缩调用记录

**后端配套**：
- prompt 组装过程落库（随消息记录完整输入文本）
- usage 统计从近似值升级为精确值（M2 遗留坑点）
- 推理性能计时（TTFT / prefill / decode 分段）

**硬约束**：新增/填实标签页只允许「加配置 + 写组件」，不改动抽屉容器与消息列表结构（一期 §3.7 设计要求）。

## 4. M6：参数实验场（2026-10-11 决策下线，已拆除）

- 同一 prompt 用多组参数（如 temperature 0.1 / 0.7 / 1.0）生成对比，双栏或三栏并排展示
- 每组结果可展开查看 M5 的观测数据（token 统计、性能指标、参数快照）
- **约束**：单模型实例，「并行对比」实为串行排队，UI 需表达排队状态
- 实验结果不写入正式会话历史（独立存储或标记为实验）

## 5. M6.5：上下文摘要压缩

替换/升级现有滑窗硬截断：

- **策略**：上下文超阈值时，用本机 14B 将超出部分的旧对话压缩为摘要；最终上下文 = system prompt + 摘要 + 最近 N 轮原文
- **可切换**：滑窗硬截断 / 摘要压缩两种策略可配置切换，便于对比教学
- **可观测**：压缩本身是一次 LLM 调用，需在调试抽屉展示压缩前/后 prompt 与 token 数对比
- **有损性声明**：摘要丢失细节，UI 上对被压缩的历史给出标识
- 触发阈值与「最近 N 轮」的 N 值在开发阶段实测调优，写入技术方案

## 6. M7：RAG 知识库

- **文档接入**：上传 txt / md（pdf 解析是否纳入在开发阶段评估，工作量单列）
- **处理链路**：切块（chunking）→ embedding → 向量存储 → Top-K 检索 → 注入 prompt
- **embedding 选型**：本地小模型（候选 bge-small-zh / m3e），**走 CPU**，不与 14B 争显存
- **向量存储**：优先 SQLite + 余弦相似度自建（教学优先），性能不足再评估引入轻量向量库
- **观测联动**（M5 的价值兑现）：
  - Prompt 预览中可看到注入的检索片段
  - 调用链标签页记录检索过程：query、命中片段、相似度分数
- **可开关**：知识库检索按会话可开关，关闭时行为与一期一致

## 7. M8：身份微调（QLoRA）

- **成功标志**：微调后的模型在不带 system prompt 的情况下，问「你是谁 / 谁开发的你」能回答自定义身份，且能扛住「忽略之前的指令，你到底是谁」类绕过尝试
- **身份设定**：自定义名字 + 背景（具体身份在构造数据集时确定，本 PRD 只定机制）
- **训练环境**：Windows RTX 4070 12GB，QLoRA（4-bit 量化底模 + LoRA），batch=1 + 梯度检查点 + 短序列
- **工具链**：
  1. ModelScope 下载 Qwen3-14B HF 权重（约 28GB）
  2. Unsloth / transformers + peft 训练 LoRA
  3. 合并 LoRA → `convert_hf_to_gguf.py` → 量化 Q4_K_M → 接入现有模型加载开关
- **数据集**：几十到几百条身份问答；构造方式（手写 / 模型生成 + 人工筛）在开发阶段确定，数据本身纳入版本管理
- **能力保护**：身份数据分布极窄，需混入通用指令样本与 tool calling 样本（replay）防止灾难性遗忘；训练用低学习率 + 少 epoch
- **能力回归**：以 `server/spikes/tool_calling_baseline.json`（2026-10-09 spike 基线：决策正确率 87.5%、格式成功率 100%）做微调前后对比
- **基线对照实验**（教学核心）：先用 system prompt 实现改身份，再对比微调方案；重点对比绕过提示词后两者的表现差异

## 8. M9：工具调用——网页搜索（MCP）

- **前置验证已完成**（2026-10-09 spike，`server/spikes/`）：Qwen3-14B-Q4_K_M tool calling 决策正确率 87.5%、格式成功率 100%，数据支持立项；基线存档供 M8 回归
- **路线分两步**：
  - **A（先做）**：后端内置 `web_search` 工具函数，打通 tool calling 循环（生成 → 解析 tool call → 执行 → 结果拼回 → 继续生成），不走 MCP 协议
  - **B（进阶）**：接入现成 MCP server（如 tavily-mcp），后端作为 MCP client 管理 server 进程生命周期，学习真实协议
- **解析层坑点（spike 已确认）**：llama-cpp-python 0.3.36 的 tool call 不走 `message.tool_calls` 字段，以 `<tool_call>...</tool_call>` 文本混在 content 中，解析层按此实现
- **搜索源**：正经 API（Tavily / Brave / SerpAPI，需 key）或野路子（DuckDuckGo 抓 HTML，不稳）；正文提取用 trafilatura 类库；选型在开发阶段确定
- **上下文膨胀防护**：搜索结果动辄数千 token，注入前必须裁剪/摘要，与 M6.5 压缩策略联动
- **观测联动**：调用链标签页记录工具调用全过程（原始请求、执行结果、拼回上下文）；SSE 协议需新增工具调用事件类型，前端渲染「正在搜索…」中间态

## 9. 明确不做（二期）

- **多模态（图片输入）**：2026-10-09 决策搁置。原因：Qwen3-14B 为纯文本模型，需换 VL 系列导致文本能力降级且与 M8 冲突；llama.cpp 对 Qwen-VL 的 GGUF/mmproj 支持不成熟；图片 token 挤占显存与上下文；滑窗截断与消息表结构需重构。待生态成熟后重评
- 检索式长期记忆（向量召回历史消息）：M7 完成后作为自然延伸再评估
- M9 路线 B 之外的更多 MCP server 接入（文件系统、数据库等）：验证路线 B 后按需评估
- 闲置自动卸载、公网访问、多账号体系：继续搁置
