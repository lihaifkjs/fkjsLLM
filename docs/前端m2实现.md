## 3. 坑点记录

开发期坑点详见 [前端web.md](前端web.md) §7，摘要：

1. 本机 Node 不在 PATH，用 Kimi 自带运行时（`%LOCALAPPDATA%/Programs/Kimi/resources/resources/runtime`）
2. Pinia `ref([])` push 原始对象后持引用修改不触发响应式——store 须返回数组内响应式代理（曾致流式卡第一帧）
3. marked 新版无 `highlight` 选项，改为渲染后 `hljs.highlightElement`，且须清 `data-highlighted` 才能随流式重高亮
4. 后台标签页 `setInterval` 被节流，mock 流式变慢——验证时保持标签可见
5. 浏览器自动化操作间隔（1–3s）慢于 mock 流式全程（约 2s），瞬时态（如「停止生成」按钮）自动化无法截获，需人工/代码走查验证
6. 停 dev server 用 `pkill -f vite` 或按 PID，勿 `taskkill //IM node.exe` 全杀
7. **局域网访问不通的经典坑（已解决）**：①vite dev 默认只绑 127.0.0.1，须加 `--host 0.0.0.0`；②Windows 首次弹出 node.exe 联网提示时若点「取消」，会自动创建**程序级入站阻止规则**，其优先级高于端口放行规则——表现为「本机通、8000(Python)通、5199(Node)不通」，解法：`Get-NetFirewallRule -Direction Inbound -Action Block | ? DisplayName -match 'node' | Remove-NetFirewallRule`（管理员）。排查方法论：用「同机不同端口/进程」做对照实验定位层级
8. **生产模式更省事**：后端 :8000 直接托管 `web/dist`，局域网只需放行 8000 一个端口；dist 须用 `VITE_API_MODE=real` 构建（否则打包进 mock）
9. **Pinia store 默认不支持 HMR**：dev 下改动 store 文件后，运行中的页面仍持有旧 store 实例，新代码调用新方法报 `xxx is not a function`（新旧代码混跑）。解法：每个 store 文件末尾加 `import.meta.hot.accept(acceptHMRUpdate(useXxxStore, import.meta.hot))`；现场应急：硬刷新页面（Ctrl+Shift+R）
